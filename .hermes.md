# MrktPltfrm — Hermes coding workflow

These instructions apply to Hermes coding tasks in this repository. Keep all existing project conventions and user changes; this completion gate does not authorize commits, pushes, deployments, or production/database writes.

## Symbolic code navigation

- Use Serena first for symbol definitions, member inspection, and semantic references when its tools are available. Load `serena-code-navigation` for the detailed workflow.
- Activate the exact repository/worktree being investigated. Use `get_symbols_overview`, scoped `find_symbol`, and `find_referencing_symbols` rather than relying solely on text matches.
- Use text search for filenames, configuration, strings, SQL, unsupported syntax, and discovery when the symbol is unknown.
- If Serena is unavailable, fails, or returns suspiciously incomplete results, report the limitation and fall back to file reads/text search. An empty reference result is not proof of no usages.
- Keep edits, execution, and tests in Hermes tools. Do not switch a shared Serena instance between different repositories during concurrent work.

## Automatic independent review before completion

For the primary agent, after implementing a feature, bug fix, refactor, or other behavior-changing task:

1. Run the relevant focused tests, compile/build, and lint checks available for the affected area. Record actual results and explicitly identify blocked checks; do not claim a clean check when it did not run. Load `requesting-code-review` for supporting verification practices. The project gate below takes precedence over that skill's optional/one-shot review skips and file-count threshold.
2. Before declaring the coding task complete, call `delegate_task` with one task using the dedicated `route: "mrktpltfrm-review"`. This trusted route selects the reviewer from the active parent chat model at dispatch, always through openai-codex (`provider: openai-codex`): GPT/Codex chats use openai-codex model `claude-opus-5.5` at Max reasoning; Claude chats use openai-codex model `gpt-6.1-sol` at Max reasoning. Unrecognized model families retain the configured fixed openai-codex reviewer fallback. Do not substitute direct Anthropic/OpenAI subscription routes or external coding CLIs. Keep the same route after switching chat models; the backend makes the selection, not the saved global main-model setting. Do not substitute an adaptive coding route or rewrite global model/reasoning settings. If this route, conditional-routing support, or the selected provider/model is unavailable, report review as blocked and request activation/access rather than silently substituting a model or self-review. Verify actual child runtime provider/model/effort metadata instead of relying on reviewer self-identification.
3. Give the fresh reviewer the repository/worktree path, original task and acceptance criteria, the task's changed paths (including in-scope untracked files), baseline commit/range where applicable, and check commands/results. Identify pre-existing changes so they are not mistaken for this task's work. Do not use `HEAD~1` as a substitute for an empty working-tree diff. Have the reviewer inspect actual files and relevant callers/tests rather than relying on the implementer's summary.
4. Require a findings-only review covering correctness, contract compliance, regressions, security, relevant C#, database usage, UI design concerns, and test coverage. The reviewer must not edit source, stage, commit, push, install dependencies, or perform production/database-writing checks. Return prioritized concrete findings with `path:line`, trigger/consequence, fix direction, a verdict, and what was executed versus only inspected. Load applicable MrktPltfrm skills for the changed area, not every project skill indiscriminately. Preference-level nits do not block completion.
5. Wait for the review result before claiming completion. For background delegation, return only a pending-review status and end the turn so completion can arrive; do not poll. The primary agent evaluates findings against the original requirements and fixes only confirmed, in-scope defects. Document any finding rejected with evidence; do not dismiss one merely because the implementer disagrees.
6. After fixes, rerun affected checks and request fresh re-review of the current changes, including previous findings. Allow at most **two fix-and-re-review rounds after the initial review**. If blocking defects remain, stop and report them to the user; do not loop indefinitely or claim the task is complete. Failed dispatch, unavailable authentication, or an unparseable/missing verdict is blocked review, not approval.
7. Finish with a short report of changes, checks, independent review outcome, and any limitations. Review approval is not permission to stage, commit, push, or deploy; obtain explicit user authorization for those actions.

## Scope and exceptions

- The user can explicitly request skipping independent review for a task.
- Pure documentation or non-behavioral configuration changes do not require this gate unless the user asks. Configuration affecting runtime behavior, security, build, or deployment does require it.
- This gate belongs to the primary coding agent. Implementation subagents return their evidence and an unreviewed handoff to the parent; they do not start their own review cascade.
- A subagent acting as the independent reviewer only reviews and reports findings. It must not implement fixes or launch another reviewer. The parent handles fixes and any re-review.

This is an agent-followed completion policy, not an enforced Git/CI or Kanban approval gate. It loads in fresh Hermes sessions; do not rebuild a running conversation's cached system prompt or tool schema to activate it.
