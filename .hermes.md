# MrktPltfrm — Hermes coding workflow

These instructions apply to Hermes coding tasks in this repository. Keep all existing project conventions and user changes; this completion gate does not authorize commits, pushes, deployments, or production/database writes.

## Symbolic code navigation

- Use Serena first for symbol definitions, member inspection, and semantic references when its tools are available. Load `serena-code-navigation` for the detailed workflow.
- Activate the exact repository/worktree being investigated. Use `get_symbols_overview`, scoped `find_symbol`, and `find_referencing_symbols` rather than relying solely on text matches.
- Use text search for filenames, configuration, strings, SQL, unsupported syntax, and discovery when the symbol is unknown.
- If Serena is unavailable, fails, or returns suspiciously incomplete results, report the limitation and fall back to file reads/text search. An empty reference result is not proof of no usages.
- Keep edits, execution, and tests in Hermes tools. Do not switch a shared Serena instance between different repositories during concurrent work.

## Automatic independent review before completion

For the primary agent, after implementing a feature, bug fix, refactor, or other behavior-changing task:

1. Run the relevant focused tests, compile/build, and lint checks available for the affected area. Record actual results and explicitly identify blocked checks; do not claim a clean check when it did not run. Load `requesting-code-review` for supporting verification practices. The project gate below takes precedence over that skill's optional/one-shot review skips and file-count threshold.
2. Before declaring the coding task complete, get two independent reviews. Call `delegate_task` once with two `tasks` entries, each with its own `route` inside the entry; a top-level `route` is ignored. The two reviewers run in parallel:
   - `route: "mrktpltfrm-review"`, the cross-family reviewer. The backend selects it from the active parent model at dispatch: a GPT/Codex parent gets Claude Opus 5.5 at xhigh through anthropic (logged as `provider=anthropic model=claude-opus-5-5`), and a Claude parent gets GPT-6.1 Sol at max through openai-codex (`provider=openai-codex model=gpt-6.1-sol`). Other model families get the route's configured fallback.
   - `route: "mrktpltfrm-review-grok"`: Grok 4.7 at xhigh through GitHub Copilot (`provider=copilot model=grok-4.7`), whatever the parent model.

   Give both reviewers the same brief (steps 3 and 4). Keep both routes after switching chat models; the backend makes the selection, not the saved global main-model setting. Do not substitute other routes, providers or models, an adaptive coding route, self-review, or external coding CLIs, and do not rewrite global model/reasoning settings. If a route, conditional-routing support, or a selected provider/model is unavailable, report review as blocked and request activation/access. Verify each child's actual runtime provider/model/effort metadata instead of relying on reviewer self-identification. One-shot sessions, including Kanban workers, have a subagent budget sized for these reviews (two reviewers in each of three rounds), so use `delegate_task` only for them.
3. Give each fresh reviewer the repository/worktree path, original task and acceptance criteria, the task's changed paths (including in-scope untracked files), baseline commit/range where applicable, and check commands/results. Identify pre-existing changes so they are not mistaken for this task's work. Do not use `HEAD~1` as a substitute for an empty working-tree diff. Have the reviewers inspect actual files and relevant callers/tests rather than relying on the implementer's summary.
4. Require a findings-only review covering correctness, contract compliance, regressions, security, relevant C#, database usage, UI design concerns, and test coverage. Reviewers must not edit source, stage, commit, push, install dependencies, or perform production/database-writing checks. Return prioritized concrete findings with `path:line`, trigger/consequence, fix direction, a verdict, and what was executed versus only inspected. Load applicable MrktPltfrm skills for the changed area, not every project skill indiscriminately. Preference-level nits do not block completion.
5. Wait for both review results before claiming completion. For background delegation, return only a pending-review status and end the turn so completion can arrive; do not poll. The primary agent evaluates both reviewers' findings against the original requirements and fixes only confirmed, in-scope defects. Document any finding rejected with evidence; do not dismiss one merely because the implementer disagrees.
6. After fixes, rerun affected checks and request a fresh re-review of the current changes from both reviewers, in one call as in step 2, including previous findings. The changes are approved only when both reviewers approve the same current changes. Allow at most **two fix-and-re-review rounds after the initial review**. If blocking defects remain, stop and report them to the user; do not loop indefinitely or claim the task is complete. Failed dispatch, unavailable authentication, or an unparseable/missing verdict from either reviewer is blocked review, not approval.
7. Finish with a short report of changes, checks, both independent review outcomes, and any limitations. Review approval is not permission to stage, commit, push, or deploy; obtain explicit user authorization for those actions.

## Scope and exceptions

- The user can explicitly request skipping independent review for a task.
- Pure documentation or non-behavioral configuration changes do not require this gate unless the user asks. Configuration affecting runtime behavior, security, build, or deployment does require it.
- This gate belongs to the primary coding agent. Implementation subagents return their evidence and an unreviewed handoff to the parent; they do not start their own review cascade.
- A subagent acting as an independent reviewer only reviews and reports findings. It must not implement fixes or launch another reviewer. The parent handles fixes and any re-review.

This is an agent-followed completion policy, not an enforced Git/CI or Kanban approval gate. It loads in fresh Hermes sessions; do not rebuild a running conversation's cached system prompt or tool schema to activate it.
